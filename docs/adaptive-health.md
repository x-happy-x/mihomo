# Адаптивные проверки серверов (MIHOMO-2)

Опциональная функция этого форка; upstream Mihomo её не поддерживает.
Перенесён подход KVN из коммита `4116c55c528a7e369da76e8e54c9ba2858b3675a`:
[PingStats.kt](https://github.com/x-happy-x/kvn/blob/4116c55c528a7e369da76e8e54c9ba2858b3675a/android/app/src/main/java/io/kvn/client/data/PingStats.kt)
и [testnode.go](https://github.com/x-happy-x/kvn/blob/4116c55c528a7e369da76e8e54c9ba2858b3675a/core/testnode.go).
Полный мобильный анализатор DNS/SNI и Android-определение Wi-Fi/оператора
не переносились: здесь проверяется GET через outbound и прямые контрольные адреса.

## Включение

В существующем `proxy-providers.ROUTER` замените только блок `health-check`
примером из [adaptive-health.example.yaml](adaptive-health.example.yaml).
Сохраните URL подписки, заголовки устройства, path и остальные поля провайдера.
Понадобится собранный бинарник MIHOMO-2. Файл-пример — фрагмент, не полный конфиг.

Функция по умолчанию выключена. При включении обязательны `health-check.enable`
и ненулевой интервал (по умолчанию 300 секунд). Для непрерывного наблюдения нужен
`lazy: false` у провайдера. Значения `timeout` — миллисекунды, `interval` — секунды.

Автоматический выбор группы включается через `type: fallback` и `use: [ROUTER]`.
Группы `select` остаются ручными. Менять их все автоматически нельзя: группы
с правилами, DIRECT, Tailscale и OLCRTC имеют другое назначение.

## Что именно проверяется

Каждый узел открывает адреса `adaptive.targets` своим outbound, не переключая
рабочие группы и не разрывая существующие соединения. Используется GET с обычной
проверкой TLS-сертификата, ожидаемым HTTP-статусом и чтением до 64 КиБ тела.
Таймаут/обрыв тела или недостаток `min-bytes` означает неуспех. Редиректы не
переходятся автоматически: разрешить их статусы можно явно в `expected-status`.

Для автоматического выбора необходим успех всех targets. Доступ к Cloudflare
при недоступном Google означает частичную связность, а не исправный узел.
Незавершённые проверки тоже не дают положительной оценки. Выбирайте адреса,
которые должны открываться для вашего трафика. История старой политики «один
успешный target» не используется: новая политика начинает отдельную статистику.
Для проверки обрыва после 16–20 КиБ укажите известный ресурс с ответом не меньше
32 КиБ и `min-bytes: 32768`. Тест с пустым ответом 204 такого обрыва не обнаружит.

Каждый список содержит 1–4 адреса. В `targets` по умолчанию Google (200, 1 КиБ)
и Cloudflare trace (200, 64 байта). Их доступность не гарантирована: можно задать
свои контрольные ресурсы. Пробы дают этап (`dial`, `tls/http`, `http`, `body`,
`ok`), HTTP-статус, прочитанные байты и время полного теста. Ошибка `dial` может
включать DNS/подключение к прокси; отдельного доказательства DNS или TCP здесь нет.

## Настраиваемые проверки сервисов (MIHOMO-5)

Для ИИ и других сервисов используйте отдельный именованный провайдер и fallback
с `use` только этого провайдера. [Пример YAML](adaptive-ai.example.yaml) показывает
проверку страницы ChatGPT. Это шаблон для настройки, а не проверенный на ваших VPN
детектор работоспособности чата. Сверьте статусы и содержимое через заведомо рабочий
и нерабочий выход; вход в аккаунт, отправка сообщений и лимиты аккаунта этим GET
не проверяются. HTTP 403/429 сами по себе не доказывают блокировку IP: причиной
может быть защита сайта или ограничение частоты запросов.

Новые необязательные поля у каждой цели (`targets`, `direct-allowed`, `direct-global`):

- `timeout`: миллисекунды, 1..60000; 0 или отсутствие наследует `health-check.timeout`.
  Может быть больше таймаута провайдера; внешний дедлайн ручного теста группы
  всё равно ограничивает запрос. Для ручного теста задавайте группе подходящий `timeout`.
- `content-type`: точный MIME-тип без параметров, например `application/json`.
  Параметр `charset` в ответе игнорируется; HTML вместо ожидаемого JSON — ошибка.
- `body-regex`: обязательное совпадение с содержимым ответа.
- `body-not-regex`: любое совпадение означает ошибку, даже если положительный
  шаблон тоже совпал. Подходит для явных признаков challenge/региональной блокировки.

Шаблоны — Go RE2, до 4096 байт; `(?i)` включает нечувствительность к регистру.
Они компилируются при загрузке конфига; неверный шаблон отклоняется до запуска.
Проверяется только первый 64 КиБ тела; сжатие не запрашивается и автоматическая
распаковка отключена. Endpoint должен возвращать обычный текст/JSON/HTML.
Совпадение за этим пределом не видно. Текст ответа и cookies не сохраняются в API
или истории. URL и краткая причина отказа видны в результатах; не помещайте секреты
в URL. Отсутствие запрещённого текста само по себе не подтверждает исправность:
задавайте положительное условие, соответствующее выбранному endpoint.

Все заданные условия и все цели обязательны. Запросы остаются GET, без перехода
по редиректам. Платные запросы к моделям, авторизация и браузерные challenge не
выполняются. Не считайте успешным статус страницы защиты только ради зелёного индикатора.

Новые поля `adaptive`:

- `failure-threshold`: 1..10, по умолчанию 1. После успешного восстановления
  доступность сохраняется до этого числа ошибок подряд.
- `recovery-threshold`: 1..10, по умолчанию 1. Для первоначального допуска и
  восстановления требуется это число успехов подряд.

При `failure-threshold: 3` первая и вторая ошибки не исключают текущий сервер;
третья исключает его из доступных кандидатов. Fallback удерживает текущий выбор
на протяжении этого допуска, даже если исторический рейтинг уже снизился.
Если нет доступных альтернатив, сохраняется прежний выбор по обычной логике fallback.
Успех сбрасывает серию ошибок, ошибка — серию успехов. Смена режима, обновление
экземпляра узла, перезапуск или устаревание результатов не наследуют этот допуск.
Завершённые ручные проверки тоже учитываются в сериях; отменённый ручной тест не
меняет доступность. Исторические счётчики по-прежнему
пополняет полный обход. Это порог числа проверок, а не гарантированное время ожидания.

В API результата узла `ok` — исход последней пробы, `available` — допуск с учётом
порогов, `consecutiveSuccesses`/`consecutiveFailures` — серии, ограниченные порогом.
Для фактического выбора дополнительно требуются подтверждённый режим и свежесть;
`available: true` в старом снимке не означает текущую доступность.
Старые панели могут отображать только `ok`; свежая ошибка остаётся видимой, даже
если fallback ещё удерживает соединение. Нестандартные таймауты учитываются в сроке
свежести: `max(2 * interval, 2 * сумма таймаутов targets) + 1 секунда`.
Секундный запас компенсирует погрешность планировщика на коротких интервалах.

У провайдеров ChatGPT/Claude/Gemini — отдельная история normal/whitelist за счёт
разных имён и политик. Нужны отдельные экземпляры провайдеров, а не три группы над
одним `ROUTER`: группы одного провайдера используют его общую проверку. Добавляйте
уникальный `override.additional-prefix`, чтобы имена узлов различались в панели.
Можно использовать один исходный файл подписки, но обновлением этого файла должен
управлять один источник. Суммарная нагрузка растёт с количеством провайдеров;
начните с небольшого списка кандидатов и `concurrency: 1..2` на сервис.

Новые поля необязательны: старые конфиги сохраняют прежнюю логику и ключ истории
при порогах по умолчанию. Изменение условий создаёт отдельную историю. В этом
изменении нет автоматической миграции конфига роутера или нового интерфейса Zashboard.

## Каскад: подписка -> проверки сервисов (MIHOMO-6)

В `adaptive` сервисного провайдера задайте `depends-on: ROUTER`, где `ROUTER` —
имя существующего провайдера с включённой базовой adaptive-проверкой. Сам `ROUTER`
не должен иметь `depends-on`. Одна базовая проверка может обслуживать несколько
независимых сервисных провайдеров. Пример — [adaptive-ai.example.yaml](adaptive-ai.example.yaml).

Базовый провайдер продолжает проверять **весь свой список**, включая ранее
нерабочие узлы. Сервисный провайдер отправляет GET только когда для такого же
подключения в базовом провайдере есть свежий успешный результат, достигнут порог
восстановления и подтверждён тот же режим сети. Последняя ошибка базы закрывает
допуск к дополнительным проверкам даже в период `failure-threshold` базы.
Это относится и к ручной сервисной проверке, и к штатным HEAD-проверкам сервисного
провайдера. Прямые контрольные пробы режима продолжают выполняться независимо.

Новый, удалённый, ещё не проверенный, устаревший или не прошедший базу узел получает
в API `skipped: dependency-not-ready`, без запросов к сервису и без прибавления
ошибки/проверки в историческую статистику сервиса. Пропуск сбрасывает текущий допуск
и серии успехов/ошибок сервиса; после восстановления базы сервис проходит свой
порог восстановления заново. `dependsOn` в снимке указывает имя базового провайдера.
История доступности ИИ не служит обходом базового допуска при выборе fallback.
Если подходящих кандидатов нет вообще, действует прежнее сохранение последнего
выбора группы; каскад не запрещает пользовательский трафик и не удаляет узлы из UI.

Допуск проверяется перед запросом и после него, а также перед записью статистики.
Если база перестала проходить проверку во время запроса, результат не попадает в
историю сервиса. Уже отправленный запрос не прерывается немедленно этим событием:
его ограничивает штатный таймаут. Планировщики независимы: восстановившийся узел
попадёт в следующий обход сервиса (или ручную проверку), а не обязательно мгновенно.
После старта сервис может пропустить первый обход, пока база ещё собирает результаты.

Провайдеры должны содержать одинаковые **параметры подключения после override**.
Сопоставление — внутренний SHA-256 канонического YAML этих параметров, включая
учётные данные и настройки транспорта, без имени узла. Это не прежний исторический
ключ по адресу: два разных аккаунта на одном IP не получают допуск друг от друга.
Различающиеся префиксы/имена допускаются. Различающиеся соединительные override или
явное/неявное задание параметра могут дать разные ключи; надёжнее использовать один
исходный файл и только разные имена/фильтры. Хэш и исходные секреты не выдаются в API.

`depends-on` **не копирует подписку**: у каждого провайдера остаётся свой источник
узлов и политика targets. Настройте одинаковый источник/файл и при необходимости
узкий фильтр для сервисов. Отсутствующий источник, выключенный adaptive, ссылка
на себя, циклы и многоступенчатые цепочки отклоняются при разборе конфига. Сейчас
поддерживается один уровень: база -> сервисы. Без `depends-on` поведение прежнее.

В старой панели результаты-пропуски могут входить в число строк последнего обхода;
для количества выполненных проверок используйте исторический `record.checks`.
Отдельная визуализация пропусков в Zashboard в эту правку не входит.

## Режим сети

Контрольные запросы `direct-allowed` и `direct-global` идут через DIRECT outbound,
минуя группы и правила Mihomo. DNS, маршруты ОС и routing-mark остаются штатными.

- `normal`: отвечает хотя бы один `direct-global`.
- `whitelist`: хотя бы один `direct-allowed` отвечает, ни один `direct-global` не отвечает.
- `offline`: не ответили обе категории. Это наблюдаемый результат, а не доказательство
  физического отключения интернета.
- `unknown`: после запуска ещё нет подтверждённого состояния.

`whitelist` означает признаки ограничения, а не доказательство действий оператора.
По умолчанию изменение подтверждается двумя последовательными наблюдениями.
Контрольные пробы в начале и конце полного обхода считаются отдельными наблюдениями.
Если они согласованы, первый обход уже записывается в статистику; ждать второго
обхода всех серверов не требуется.
В API `observed` может отличаться от подтверждённого `mode` во время перехода.
Пока режим не подтверждён, результаты не записываются в normal/whitelist.
Прямые контроли повторяются после обхода узлов: если сеть за это время поменялась,
весь пакет не попадает в историю стабильности. Такой контроль не исключает
кратковременное изменение сети между контрольными запросами.

При неизвестном режиме, переходе или отсутствии свежих проверок fallback
сохраняет выбор согласно MIHOMO-1; он не считает старую статистику доступностью.

## Статистика и порядок

Для normal и whitelist — отдельные рейтинги. Как в KVN, счётчики успехов/неудач
на каждой проверке умножаются на 0.9, задержка успешных проверок сглаживается
с весами 0.7/0.3. Вероятность успеха: `(ok + 1) / (ok + fail + 2)`;
оценка: `successRate * 1000 / (avgMs + 100)`. У нового узла оценка 0.9.

Стабильный узел: минимум 3 проверки, вероятность >= 0.7, последняя проверка
успешна и не старше 7 суток. Они проверяются первыми, остальные — по оценке.
Каждый цикл проверяет весь список: новые и плохие узлы не исключаются навсегда.
По умолчанию одновременно проверяются 4 узла (`concurrency: 1..10`).

Результат каждой пробы доступен до завершения всего обхода. Рейтинг обновляется
после контрольной проверки режима в конце цикла. `fallback` использует порядок
провайдера и реальные GET-результаты; ручной выбор запускает свежую GET-проверку.
Явные `proxies` и порядок разных `use`/регулярных фильтров группы сохраняют свою
семантику; объединённого рейтинга между разными провайдерами нет.

История сохраняется в штатном cache.db, в отдельном ключе storage. Хранится до
500 записей на режим, срок хранения 30 дней. Старые URL/учётные данные подписки
не сохраняются. Идентичность — хэш типа протокола и адреса:порта (при отсутствии
адреса — имени), поэтому переименование сервера сохраняет статистику. Разные
учётные записи одного протокола на одном адресе делят историю; свежая доступность
всегда привязана к конкретному экземпляру узла и не переносится на его замену.

`network-key` разделяет историю разных uplink-профилей, если вы меняете их конфигом.
Автоматического обнаружения мобильного оператора/Wi-Fi, как на Android, нет.
Изменение провайдера, network-key или параметров adaptive создаёт отдельную историю.
После перезапуска рейтинг восстанавливается, режим и доступность проверяются заново.

## API и совместимость

`GET /providers/proxies/ROUTER` возвращает дополнительно объект `adaptive`:
`mode`, `observed`, `pending`, `checkedAt`, прямые результаты `directAllowed` и
`directGlobal`, `rankings.normal`, `rankings.whitelist`, результаты узлов `results`.
В рейтингах есть `stable`, `score`, `successRate` и статистика `record`.
Новые административные API и права доступа не добавляются.

Штатные HEAD-проверки провайдера и дополнительные URL групп продолжают выполняться
после адаптивного обхода для совместимости с историей задержек Zashboard.
Поэтому число миллисекунд в существующем интерфейсе может отличаться от результата
GET в `adaptive`. Zashboard и HomeNet в этой задаче не изменялись.
Адаптивная доступность влияет на fallback; url-test продолжает штатную логику.

Отключить: `adaptive.enable: false` и применить конфиг обычным способом.
Удалять cache.db для отключения не нужно. Эта задача не устанавливает обновление
на роутер и не включает проверки OLCRTC/Tailscale автоматически.

- `go test -race ./adapter/provider ./adapter/outboundgroup`
- `go test ./config ./hub/route`
- `python scripts/test-adaptive-health.py --binary dist/mihomo-MIHOMO-2-windows-amd64.exe`

Последний тест запускает отдельный локальный Mihomo и локальные HTTP-прокси:
normal -> whitelist -> normal. Он не использует роутер, подписки или интернет.
