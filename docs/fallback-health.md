# Fallback: сохранение выбора и несколько проверок

Изменение этого форка (MIHOMO-1). Требуется обновлённый бинарник: поле
`health-check-urls` не является штатной настройкой upstream Mihomo.

## Выбор сервера

- Ручной выбор сохраняется, пока хотя бы одна проверка этого узла успешна.
- Если выбранный узел не проходит проверки, но другой проходит, используется
  первый доступный узел по порядку группы, ручная фиксация снимается.
- Если все проверки неуспешны, сохраняется ручной выбор, иначе текущий узел.
- Первый узел используется только при отсутствии сохранённого доступного
  в списке выбора (например, при первом запуске или удалении узла из подписки).
- После восстановления проверок действует обычный приоритет fallback.
  Состояние текущего узла хранится в памяти; это не новая гарантия восстановления
  выбора после перезапуска. Постоянная ручная фиксация независимо от состояния
  других узлов по-прежнему делается внешней группой `select`.

## Дополнительные проверки

`url` остаётся основным адресом. В `health-check-urls` можно указать до четырёх
дополнительных HTTP(S) адресов. Дубликаты удаляются. Успех хотя бы одного
адреса достаточен для fallback. Неизвестный результат дополнительного адреса
не считается успехом. Применяется общий `expected-status` группы.

```yaml
proxy-groups:
  - name: EU-AUTO
    type: fallback
    use: [ROUTER]
    filter: '(🇪🇺|🇩🇪|🇫🇮|🇸🇪|🇳🇱|🇵🇱|🇫🇷|🇨🇭|🇮🇹|🇭🇺|🇳🇴|🇪🇪|🇱🇹|🇱🇻|🇬🇧)'
    url: https://www.gstatic.com/generate_204
    health-check-urls:
      - https://cp.cloudflare.com/generate_204
    expected-status: '204'
    interval: 300
    timeout: 5000
    lazy: false
```

Адреса в примере — кандидаты: их доступность нужно проверить через реальные
серверы. Для RU выбирайте подходящие RU-адреса с соответствующим ожидаемым
HTTP-статусом. Не добавляйте в проверку VPN-группы сайт, доступность которого
не означает пригодность узла для нужных вам сервисов: доступность одного
сайта не гарантирует доступность всех остальных.

Проверки выполняет существующий планировщик провайдера. Для узлов из `use`
укажите в существующем `proxy-providers.ROUTER.health-check`:

```yaml
enable: true
interval: 300
timeout: 5000
lazy: false
```

Сохраните остальные поля провайдера. Его интервал и lazy управляют проверками
узлов подписки; `lazy: false` только у группы недостаточно. Для явных `proxies`
применяются настройки группы. Дополнительные URL повышают количество запросов
пропорционально числу адресов. Проверки OLCRTC автоматически не включайте.

В API группы добавлено `healthCheckUrls`; `testUrl` сохраняет прежний смысл.
Zashboard может продолжать показывать отсутствие задержки для основного URL,
хотя fallback использует успех дополнительного. Результаты отдельных URL
доступны в `extra` узла. UI в этой задаче не менялся.

Смена узла применяется к новым соединениям, существующие соединения эта правка
не закрывает. Результаты берутся из последних проверок планировщика, а не из
успеха пользовательского трафика. При отказе всех тестов сохранение текущего
узла не является доказательством его работоспособности.

## Проверка

`go test ./adapter/outboundgroup ./adapter/provider`

`go test -race ./adapter/outboundgroup`

Покрыты общий отказ, ручной выбор, восстановление, приоритет, удаление узла,
независимый второй URL, регистрация проверок при парсинге и конкурентный API.
Изменение исходников само по себе не меняет конфигурацию или бинарник роутера.
